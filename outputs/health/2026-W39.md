## 1. Catalogue integrity

`wiki/index.md` has 32 data rows; `wiki/pages/` + `wiki/stars/` together have 32 files. Every slug in the index resolves to a file and vice versa — no missing rows, no orphaned files, no duplicate or missing `canonical_id`, and every `status` value is a valid `draft|verified|deprecated`. Two sub-issues found, not fixed (need Josep's judgement, not mechanical):

**a) `type: repo` rows filed under `wiki/pages/` instead of `wiki/stars/`, with date-slugs instead of `<owner>--<repo>`:**
- `20260918-obsidian-skills` (wiki/pages/20260918-obsidian-skills.md) — `captured_by: routine:capture-link`
- `20260920-fast-jev-compaction` (wiki/pages/20260920-fast-jev-compaction.md) — `captured_by: routine:capture-link`

These aren't broken (both files exist and are well-formed) — they were captured one-off via `vault-capture`, not via `github-stars-sync`, so CLAUDE.md's "`type: repo` → `wiki/stars/<owner>--<repo>.md`" rule (written for the stars-sync routine) doesn't cleanly apply. But it does mean any tooling that keys off `type: repo` to find the file (as this lint script initially did) will guess wrong. Worth a decision: either carve out an explicit exception in CLAUDE.md for ad-hoc repo captures, or use a different `type` (e.g. `tool`) for one-off GitHub captures that go through `vault-capture` rather than the stars sync.

**b) 8 star pages are missing `author` and have a malformed `captured_at`** (both `+00:00` offset *and* a trailing `Z`, e.g. `"2026-09-19T11:09:28.035525+00:00Z"` — not valid ISO-8601, so nothing downstream that parses it strictly will succeed):
- `wiki/stars/DietrichGebert--ponytail.md`
- `wiki/stars/Panniantong--Agent-Reach.md`
- `wiki/stars/ScrapeGraphAI--Scrapegraph-ai.md`
- `wiki/stars/cathrynlavery--diagram-design.md`
- `wiki/stars/googleanalytics--google-analytics-mcp.md`
- `wiki/stars/jackwener--OpenCLI.md`
- `wiki/stars/lewislulu--html-ppt-skill.md`
- `wiki/stars/m-bain--whisperX.md`

All 8 share the same `captured_at` minute (`2026-09-19T11:09:28.03…`), i.e. one `github-stars-sync` run produced malformed frontmatter for its whole batch while every other run (21 other star pages, different timestamps) is clean. This looks like a bug in that specific run rather than the routine itself, but it's worth checking `routines/github-stars-sync.md`'s timestamp-generation step if it recurs. Left as data (not "safe mechanical" — fixing frontmatter counts as rewriting a page), flagged here for a manual patch or a targeted re-run.
